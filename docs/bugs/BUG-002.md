# BUG-002: Repeated partial refunds can exceed the amount paid

| Field | Value |
|---|---|
| Severity | Critical |
| Priority | High |
| Component | `refund_payment` (db/02_functions.sql) |
| Rule | R06: total refunded for a payment never exceeds the amount paid |
| Found by | DQ-005, DQ-000 (step S02-04) |
| Fix | Pull request #1 |

## Environment

PostgreSQL 17, isolation level READ COMMITTED, time zone UTC.
Local (Windows, Git Bash) and CI (GitHub Actions, Ubuntu 24.04).

## Precondition

Order `ORD-B002` is paid with one captured payment `PAY-B002` of 100.00.

## Steps to reproduce

1. Refund 60.00 on `PAY-B002`: `refund_payment('RF-B002-1', 'PAY-B002', 60.00, ...)`.
2. Refund 60.00 again on `PAY-B002`: `refund_payment('RF-B002-2', 'PAY-B002', 60.00, ...)`.

## Expected result

Step 1 returns `OK`. Step 2 returns `REFUND_EXCEEDS_PAID`, because 60.00 + 60.00 = 120.00 is more than the 100.00 paid.
No second refund is saved.

## Actual result

Both steps return `OK`. The payment now has 120.00 in refunds for 100.00 paid.

## Evidence

CI run on the test commit (red): https://github.com/pauloafonsofh/ecommerce-data-quality-lab/actions/runs/39943519198

```
DQ-000   scenario steps return expected status          1  FAIL
           | S02-04|REFUND_EXCEEDS_PAID|OK
DQ-005   refunds never exceed payment                   1  FAIL
           | PAY-B002|100.00|120.00|20.00
```

Check DQ-005 (`checks/DQ-005_refunds_never_exceed_payment.sql`) lists every payment whose refunds add up to more than the amount paid.

## Root cause

`refund_payment` compares each new refund with the payment amount alone. It never adds the refunds that already exist for the same payment.

## Impact

From `impact/BUG-002_impact.sql`, on the lab data set:

| payments_over_refunded | excess_refunded |
|---|---|
| 1 | 20.00 |

Each extra refund is direct money loss. With real traffic, any payment that gets two or more partial refunds is exposed.

## Blast radius

All payments with more than one refund. Full refunds made in a single step are not affected.
Two refunds sent at the same time can also pass a "sum then compare" check unless the payment row is locked
(this race is covered with BUG-001).

## Data remediation

Recovering the excess money is a business decision (contact the customer or absorb the loss), so no data is changed by this fix.
The impact query lists the affected payments and the amount to recover.

## Fix

`refund_payment` now locks the payment row (`SELECT ... FOR UPDATE`), adds the refunds already made, and rejects the
new refund when the total would be greater than the amount paid. DQ-005 stays in the suite as a regression check.
