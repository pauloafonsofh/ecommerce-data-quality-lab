# BUG-005: Daily revenue report double-counts orders with several items or payments

| Field | Value |
|---|---|
| Severity | Major |
| Priority | High |
| Component | view `daily_revenue` (db/03_views.sql) |
| Rules | R07: report = independent sum; R08: report = hand-computed values |
| Found by | DQ-006, DQ-007 |
| Fix | Pull request #2 |

## Environment

PostgreSQL 17, isolation level READ COMMITTED, time zone UTC.
Local (Windows, Git Bash) and CI (GitHub Actions, Ubuntu 24.04).

## Precondition

Scenario S03 (`scenarios/S03_revenue_fixture.sql`), with values computed by hand:

- `ORD-F1`: 2 item rows (1 x 50.00 and 2 x 50.00 = 150.00), paid on 2026-03-10 in two payments (100.00 + 50.00).
- `ORD-F2`: 1 item (1 x 80.00), created on 2026-03-09, paid on 2026-03-10 (80.00).
- `RF-F2`: refund of 30.00 on 2026-03-11.

## Steps to reproduce

1. Load the scenario.
2. `SELECT * FROM daily_revenue WHERE day BETWEEN '2026-03-10' AND '2026-03-11';`

## Expected result

| day | items_sold | gross_revenue | refunds | net_revenue |
|---|---|---|---|---|
| 2026-03-10 | 4 | 230.00 | 0.00 | 230.00 |
| 2026-03-11 | 0 | 0.00 | 30.00 | -30.00 |

## Actual result

| day | items_sold | gross_revenue | refunds | net_revenue |
|---|---|---|---|---|
| 2026-03-10 | 7 | 380.00 | 0.00 | 380.00 |
| 2026-03-11 | 0 | 0.00 | 30.00 | -30.00 |

`ORD-F1` has 2 item rows and 2 payments, so the join creates 2 x 2 = 4 rows:
items (1 + 2) x 2 = 6 instead of 3, and payments (100 + 50) x 2 = 300.00 instead of 150.00.
Refunds are correct, because they are added up in a separate step.

## Evidence

CI run on the test commit (red): https://github.com/pauloafonsofh/ecommerce-data-quality-lab/actions/runs/39945170414

```
DQ-006   daily revenue matches independent sum      2  FAIL
           | 2026-02-20|3|3|179.40|89.70|0|0
           | 2026-03-10|7|4|380.00|230.00|0|0
DQ-007   daily revenue matches hand oracle          3  FAIL
           | 2026-03-10|items_sold|4|7
           | 2026-03-10|gross_revenue|230.00|380.00
           | 2026-03-10|net_revenue|230.00|380.00
```

DQ-006 rebuilds every number from the tables in separate steps and compares day by day.
DQ-007 compares the report with the values computed by hand, so it still works if DQ-006 had a mistake.

## Root cause

The view joins orders, order items and payments row by row and only then adds up.
Each payment is repeated once per item row, and each item once per payment.
Orders with one item and one payment look correct, which is why the defect passes a quick review.

## Impact

From `impact/BUG-005_impact.sql`, on the lab data set:

| days_affected | revenue_overstated |
|---|---|
| 2 | 239.70 |

An order with 2 or more item rows overstates `gross_revenue`; an order with 2 or more payments overstates `items_sold`.
Decisions based on this report (sales targets, commissions, stock planning) use numbers that are too high.

## Blast radius

The `daily_revenue` report only. Stored data (orders, payments, refunds) is correct.

## Data remediation

None needed: the report is a view, so it is recalculated from correct data as soon as the fix is deployed.
Reports already exported or shared before the fix must be produced again for the affected days.

## Fix

The view now adds up items per order and captured payments per order and day in separate steps,
and only then joins them. DQ-006 and DQ-007 stay in the suite as regression checks.

## Follow-up found in review

An independent review of the fix found one more case: an order paid in parts on two different days
had its items counted on both days. The check DQ-006 used the same rule as the view, so it could not see it.
The rule is now "an order's items count once, on the day of its first captured payment".
Scenario S03 got an order paid on two days (`ORD-F3`), DQ-006 and DQ-007 were updated, and the view was fixed.
The evidence above shows S03 as it was when the report was written.
